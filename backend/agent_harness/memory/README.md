# 客户画像：自动注入与通话后更新

画像按 `workspace + customer + scenario + field` 组织，使用 PostgreSQL 的 `memory` 表保存每个字段的值、状态、版本、客户原话、消息 ID、来源会话和有效期。四场景的字段由 `customer_fields` 定义；对话 Agent 不再持有 `read_memory`、`write_memory` 工具。

## 一通电话的数据流

1. `BackendService.create_session()` 在同一事务中创建会话和 `profile_jobs` 记录，冻结本次有效画像。过期字段不注入，未知和拒答保留状态。
2. `Conversation.business_summary()` 将画像放入系统上下文，每次模型推理均可见。同一通电话里，客户最新的明确表达优先于历史画像，不需要先保存再查询。
3. `end_session()` 将任务从 `collecting` 改成 `pending`；仅有宿主开场、Agent 发言或中间转写时标记 `skipped`。此时不调用模型，所以结束通话无需等待提取。
4. `ProfileWorker` 在后台读取冻结的场景定义、通话前画像及完整的最终对话，调用一次独立模型提取字段变化。
5. `ProfileStore.apply()` 校验整批字段、类型、客户消息 ID 和逐字引用，然后在同一事务中追加画像版本、写审计并完成任务。未提到的字段保持原样。

## 模块职责

| 文件 | 职责 |
| --- | --- |
| `profiles.py` | 画像快照、任务状态、提取结果 Schema、整批校验和更新 |
| `extraction.py` | 提取提示词和一次 JSON 模型调用，默认复用业务文本模型与凭据，不提供任何工具 |
| `worker.py` | 持久队列消费、租约、超时、重试与取消恢复 |
| `persistence.py` | 字段版本、原话来源、幂等键和有效期存储 |
| `validation.py` | 值类型、枚举、长度和数值范围校验 |

提取器可以理解“资料都备齐了”为 `true`；代码核验引用确实来自当前客户的本次最终发言，但语义是否支持提取值仍由模型判断，需要通过真实样例评测。Agent 的提问可用于理解“是的”，不能单独作为写入证据。`host_control` 和中间转写不进入提取输入。

`BackendService.read_memory/write_memory` 仍是宿主内部存储接口，供导入和存储契约验证使用。内部直接写入保留原有逐字值检查；正常对话更新通过通话后任务完成。

## 顺序、有效期与恢复

每个会话只有一个任务。后台每次原子领取任务，使用 120 秒租约；提取总超时 60 秒，单次供应商请求超时 45 秒且不隐式重试。失败最多自动尝试三次，两次重试分别等待 5 秒、10 秒；最终 `failed` 保留任务和错误类别，旧画像不受影响。关闭宿主会取消后台调用并恢复为待处理，启动应用时恢复消费；崩溃遗留的活动会话先关闭并提交画像任务，过期租约可重新领取。

更新比较来源客户消息的显式数据库序号，不使用模型任务完成时间；旧通话任务不能覆盖较新的客户自述。版本与任务完成一起提交，失败整批回滚。后台延迟不会延长资料有效期：到期时间按客户消息时间加字段 TTL 计算。语义版本不同的旧字段不注入新场景。

异步任务尚未完成时，下一通电话可能暂时使用旧画像；通话开始后不反复替换已注入的快照。本次最新表达仍然优先。清理会话会取消未完成任务并清除其旧画像快照，保留已保存画像所需的来源。

## 观察与验证

`GET /api/sessions/{id}/state` 返回 `profile_update` 的 `status/attempts/error`。页面在结束后继续刷新，显示准备更新、整理中、重试、完成或失败。任务状态是 `collecting → pending → running → completed`，也可能进入 `skipped`、`retrying`、`failed` 或清理后的 `cancelled`。

```sh
uv run pytest -q tests/agent_harness/test_profiles.py tests/runtime/test_speech_pipeline.py
```

测试注入提取器或拦截 HTTP，不调用真实模型；覆盖非阻塞结束、布尔与枚举归一化、上下文提取、证据隔离、原子提交、乱序任务、超时重试和恢复。真实模型测试必须独立记录，不能由存储测试代替。
