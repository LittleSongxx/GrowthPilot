# 报名条件与准备卡点排查

## 适用与边界

- 解决“我是否存在明显条件缺项”“报名前还要准备什么”“我现在该继续哪一步”。
- 按公开依据与客户自述梳理；不是个人资格核验、审核查询或覆盖所有页面异常的故障排查。
- 仅比较工作模式、租车或保障时使用对应技能，不为了报名收集与当前问题无关的资料。

## 最少信息

- 客户具体疑问或目前自述阶段：尚未了解、准备资料、已安装、已提交等。
- 会改变资格或材料要求的配送类型；兼职意向不自动写成众包类型。
- 条款有区域差异时确认城市。
- 只询问材料是否具备或页面提示，不索取证件号码、验证码或材料图片。

## 判断与推进

1. 先定位问题属于准入条件、材料准备、操作步骤还是等待审核；不同问题不能统一回答成“下载后试试”。
2. 准入问题按适用配送类型检索具体条件，用客户自述逐项对照；年龄、车辆或健康要求没有适用依据时不凭经验作判断。
3. 明确存在缺项时，解释缺项影响和原文支持的补齐步骤；客户未提到某材料时标记待确认，不判定不符合条件。
4. 材料准备按“已具备、尚缺、未确认”形成简短清单。健康证明、培训或装备要求保留适用范围，不把服务规范中每项运营要求都改成注册前必须提交的材料。
5. 对培训或注册机制，区分已明确要求与个别区域试点；没有城市清单的试点公告不能证明客户所在地已经执行，也不能反向证明不需要培训。
6. 客户尚未安装且愿意接收下载短信时，调用 `send_download_sms` 发送当前场景的 App 下载链接，依据返回结果说明发送是否成功；后续操作根据检索到的公开说明指导。已安装从其当前阶段继续，已提交不重复要求注册。
7. 客户遇到页面问题时，先确认提示内容，再依据检索返回的对应说明给出一步操作。资料只支持准备清单时就交付清单，不编造按钮、菜单或故障原因。
8. 客户说“资料齐了”“提交了”时，仅据其自述推进；是否审核通过、能否接单、何时获批都不能从材料完整或提交成功推断。“照片模糊”等提示只定位需要检查的材料，不能据此声称已核实审核未通过或系统退回。
9. 首次配送准备仅解释已查到的培训、装备卫生和服务要求；不把公开常识清单包装成当前 App 的强制操作流程。

## 完成与停止

- 完成：客户得到当前阶段最小下一步，以及影响报名或准备的具体缺项；不要求本轮必须注册。
- 已提交等待审核且没有新问题时，说明无法读取后台状态后结束，不许诺审核期限或用重复提交解决未知问题。
- 资料不足时保留已完成的条件与材料梳理；客户拒绝或暂缓则停止推进。

## 正反例

- 正例：客户说“已经装了，健康证明还没准备”。先核对适用配送类型和材料依据，再说明该项准备要求；不重发下载步骤，也不宣称其他条件已审核通过。
- 反例：“资料准备好了就等于审核通过；培训试点已经全国执行，点击我编出的菜单就能开跑。”这将自述、试点和未知操作都写成确定事实。

## 能力依据

- `search_policy`：已配置 `meituan-rider-faq`、`meituan-rider-service-standard`、`meituan-rider-training-pilot`；分别支撑公开报名信息、服务准备要求和试点边界。
- `send_download_sms`：向当前客户发送骑手 App 下载短信；发送成功仅表示短信已发送，下载和报名进度仍以客户自述为准。
- Agent 负责自述进度定位、资料缺项分类与最小下一步组织；没有个人审核、账户操作或页面诊断接口。
- 下载链接由短信工具提供；材料、培训和操作步骤必须使用当次检索返回的适用原文，来源配置本身不能证明已经检索成功。
