# 跑单模式与时间适配

## 适用与边界

- 解决“我只有这些时间，适合了解哪种配送模式”；以条件匹配为结果，不替客户报名。
- 仅问某项报名资格时使用报名准备技能；主要担心投入回报时转入成本规划。
- 兼职、全职是客户的工作意向，不是已选择众包、专送的证据。

## 最少信息

- 可用时段及每周大致可跑天数，时段能否保持稳定。
- 客户是否需要随时上下线，还是能够接受站点安排；已有信息不重复问。
- 具体查询当地方案时需要一个明确城市；只比较模式不必先收齐地区和车辆信息。

## 判断与推进

1. 先复述真正的约束，例如“只能下班后两小时”，不先把客户归类为众包。
2. 根据当前政策原文比较自主安排与站点安排的差异。将“可跑时间”和“必须接受的安排”对照，不能把收入高低当成时间匹配证据。
3. 时段零散、必须自主安排：优先解释有依据的自主安排模式，并保留当地开放、准入和具体规则待核实项。
4. 可稳定出勤、接受站点安排：介绍站点型模式的已知要求；没有具体班次就不能断言客户的两小时能满足安排。
5. 两种模式都可能适合：围绕客户最看重的自由度或稳定安排比较，给出选择条件，不强行选出唯一答案。
6. 客户想了解本地服务时，再用当地方案补充可咨询类型；城市级方案不能变成已确认在招的具体岗位，也不能称为最近站点。
7. 若只剩班次、招募或区域开放等无法确认事项，指出这一个决策缺口；仍先交付已经完成的模式比较，不把整件事退回客户重做。
8. 客户更正时段、城市或配送类型后，按新约束重新判断，撤回不再适用的建议。

## 完成与停止

- 完成：客户知道哪种模式更符合已知时间约束、理由是什么、还缺哪个条件才能决定。
- 暂不适合固定安排、先了解再决定均是有效结果；不以下载或报名作为完成条件。
- 客户不想继续比较时结束；若问题转为收益或租赁，围绕新问题选择对应技能。

## 正反例

- 正例：客户说“我白天上班，晚上时间不固定”。先解释有依据的安排差异，确认其是否必须自由上线，再形成有条件的模式建议；不要先追问身份证和车辆资料。
- 反例：“你是兼职，所以就是众包，晚高峰每天都有单，直接下载就能跑。”这把意向、派单和准入三个未知项写成了事实。

## 能力依据

- `search_policy`：已配置 RAG 来源 `meituan-rider-faq`；依据实际返回正文解释配送模式，来源中的招募介绍不是个人获准接单的证明。
- `search_nearby_stations`：提供当前场域业务目录中的地区与配送类型方案；具体排班、实时招募和 GPS 距离不在能力范围内。
- Agent 负责约束对照、冲突识别与偏好澄清，不生成未返回的班次或订单需求。
- 来源 ID 说明资料配置范围，不证明本次检索成功；只有当次返回的适用原文可以支持政策结论。
