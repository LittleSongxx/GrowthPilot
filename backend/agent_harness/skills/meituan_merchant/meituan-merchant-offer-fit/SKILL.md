# 商家权益适配

帮助商家判断一项权益能否解决当前需要。优惠额度只是比较因素，实际适用范围、承担费用和使用计划决定其价值。

## 适用与不适用

- 适用：“新店有什么优惠”“推广券能抵配送费吗”“有券是不是就不用付钱”。
- 不适用：查询账户领券结果、代报名、保证获客或订单增长，或确认实际券余额；当前没有账户与活动执行接口。
- 客户主要在比较配送方式或经营成本时，先解决对应问题，不为了推荐活动改变客户目标。

## 最少需要的信息

- 门店城市、经营类目、客户明确自述的新老商家身份；身份未知不根据“刚下载 App”推断。
- 客户想减少哪类费用，以及是否本来就需要该服务；仅当期限会改变判断时了解预计使用时间。
- 客户指定一项活动时先确认其名称或页面规则摘要，不把查询到的另一项活动规则套进去。

## 判断与处理

1. 先明确客户要解决配送、运营还是推广支出；如果只是了解福利，先介绍查到的可选权益，不以注册或购买服务换取答案。
2. 按已知地区、类目和新老商家身份核对活动，将客户条件与结果中的适用条件逐项比较；参考或通用方案不能直接认定适用该账户。
3. 将每项权益整理为“抵什么、不能抵什么、如何取得、何时可用、是否另有支出”。只采用结果明确提供的条款，未列期限或门槛要保留未知。“指定运营服务费”没有解释具体范围时，不推定包含或排除技术服务费；未列项目是待确认，不能写成明确不可抵扣。记录的 valid_from/valid_until 只表示资料有效期，不等于活动领取起止日期；领取后可用天数另列，不拼成活动期或个人到期日。
4. 需求与使用范围冲突时直接说明不匹配，例如自配送需求不能由仅适用平台配送的券解决；无需为了用券建议客户改用无必要的服务。
5. 即使券额较大，也检查实际需要是否在期限内发生、单笔抵扣限制是否适用，以及超额费用由谁承担。不将券面额等同现金收益或实际节省额。
6. 有明确需求且条件匹配时，给出“值得核实领取资格”的建议；没有适用支出或条件不明时，可以建议暂不参加或先确认那个缺项。
7. “免费开店”与活动覆盖费用分开解释；某种券可抵扣不表示配送、技术服务或所有运营支出免费。没有返回对应规则时不能补承诺。
8. 客户自述已经领取，只能据其描述继续分析使用范围；不声称已到账或生效。需要找领取入口时仅使用已有准确原文或客户页面提示，不编按钮与菜单。
9. 客户更新经营类目、配送方式或新老身份时重新核对受影响的活动；拒绝参加后不再用优惠反复促成。

## 能力与证据依据

- `query_merchant_offers`：提供按客户自述筛选的运营、配送或推广权益，以及领取、使用和资格限制；未接入账户资格、券余额或活动核销。
- `search_policy`：当涉及“免费开店”等费用概念时，可检索来源 `meituan-merchant-faq`；技术服务费与履约费的概念可参考 `meituan-merchant-fee-components-2024` 的适用原文。
- 上述 RAG 来源不证明任何当前活动金额、期限或客户领券资格；具体权益以本次活动工具结果与其范围为依据，不能拼接历史宣传为新活动。
- 工具提供权益条件，使用需求和新老身份来自客户自述，是否值得继续核实是 Agent 的匹配判断；未返回实际订单量时不能计算预期增长或必然节省金额。

## 完成条件

客户理解该权益与自身需求的匹配或冲突、使用限制、尚待核实的资格，以及可选下一步。得出“现在用不上”也完成本技能。

## 示例

- 正例：便利店客户只想自配送，查询结果中的配送券明确仅用于平台配送订单。指出它不能减轻当前自配送支出，客户无切换需求则暂不推荐领取。
- 反例：把 100 元推广券说成“注册送 100 元现金”，忽略领取或使用限制，承诺领券后订单增长，或为了券额催客户开通付费推广。
