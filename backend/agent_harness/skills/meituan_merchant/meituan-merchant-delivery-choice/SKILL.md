# 门店配送方式选择

帮助商家判断哪种配送方式值得继续核实。先看门店能否组织配送，再比较费用；参考方案只能支持条件选择。

## 适用与不适用

- 适用：“店里就两个人，谁来送”“自己送是不是便宜”“该选平台配送还是自配送”。
- 不适用：查询实时骑手、保证送达时效、开通配送或确认某地址可用；这些能力当前未接入。
- 客户已选定方式只问一单能剩多少时，转入单笔贡献测算，不要求重新选择配送。

## 最少需要的信息

- 门店城市、经营类目；已有城市即可查询，不强制补商圈。
- 会改变选择的经营条件：忙时能否留出送单人手、客户自述的配送范围或配送需求。
- 比较费用时确认要比较的两种方式；需要金额比较才了解相同订单的计费基数和自配送成本，不为了完整画像追问订单量等无关项。

## 判断与处理

1. 确认商家当前优先解决人手、成本还是配送覆盖问题。依据客户最新表达判断，不把“店里两个人”直接等同于无法自配送。
2. 核对适用地区和类目的配送方案，分清谁组织配送、方案覆盖说明和仍待确认条件。查询到方案不代表该门店已获支持。
3. 客户明确忙时无人送单时，把平台配送作为优先核实方向；如果已有固定送单人手，则继续比较自配送的人员与配送负担。
4. 客户尚不清楚人手或配送安排时，先给出条件分支，例如“能稳定留人送单才适合进一步比较自配送成本”；不替客户假设运力充足。
5. 比较费用时，对平台配送和商家自配送分别取得对应收费方案。拆开技术服务费、履约费和商家自己承担的配送成本，不只比较一个费率。
6. 自配送成本未由客户确认时，说明费用比较尚缺这一项。目录中配送费为 `null`、未列出某项或写“商家承担成本”，均不证明平台收费为零。
7. 只有一种收费方案时，可以解释已知方案，但保留另一种的未知项，不宣布哪种更便宜；不同类目、城市或配送方式的结果不能拼成一个方案。
8. 给出与客户条件对应的建议和理由，例如“忙时无法抽人，先核实平台配送是否覆盖这家店”。具体地址可用、即时运力、最终合同价格仍需实际确认。
9. 客户更正人手、城市或类目时重新判断受影响部分。客户接受建议后可选择核实条件或继续了解费用，不把下载注册当作本技能的必经步骤。

## 能力与证据依据

- `query_delivery_options`：提供地区和类目对应的配送职责、方案范围与限制；`query_merchant_fee_plans`：提供按配送方式区分的参考收费和排除项。
- `search_policy`：解释费用概念时使用当次检索正文。来源 `meituan-merchant-fee-components-2024` 支持技术服务费与履约费的区分；其历史费率不是当前门店报价。
- 来源 `meituan-merchant-delivery-fee` 解释订单展示的配送产品与配送费，不能替代商家合同服务费。来源 ID 是证据索引，不代表该条款本次已检索到。
- 工具结果提供方案事实，忙时人手和配送需求来自客户自述；“更值得核实哪种方式”是 Agent 的条件推理，不能包装成平台核准。

费用比较须分别明确自配送的平台收费、门店配送成本和另一方案的收费；任一项未知时，不能用“平台配送多出来的费用”或“自配送能省下”暗示未知费用为零。

比较中区分责任安排与履约结果：由服务方组织配送可以减少门店抽人的需要，但不能在运力未知时承诺一定解决人手不足或一定有人接单。没有规则支持时不提出平台配送与门店自送混用的现成方案，也不建议客户已经明确无法承担的自送安排。

## 完成条件

客户已得到与经营条件对应的候选方式、影响选择的费用差异和具体待确认项。若核心条件未知，说明哪项信息会改变选择；暂不决定也是有效结果。

## 示例

- 正例：客户说“长沙餐馆，午高峰两个人都在出餐，没人送”。解释平台配送值得优先核实，说明查询方案的费用和地址覆盖未知项；客户只想了解时停在这里。
- 反例：因自配送费字段为空就说“自配送平台不收费，一定更省”，或因有城市方案就说“你这家店高峰肯定有人送”。
