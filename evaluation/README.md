# 用增 Agent 评测

从两个问题开始学习：**RAG 有没有找到相关知识？完整 Agent 有没有完成当前客户的合理目标？** 正式评测只包含 `rag` 与 `dialogue` 两类；后者直接运行文本 Agent，不包含 ASR、TTS，也不单独评价 Memory 或 Skill。

四个场景分别保存 **100 道 RAG 问题和 100 个动态客户案例**，均可单独运行。全量为 400 道 RAG 问题、400 个客户案例；对话默认让每位客户连续通话 2 次，共产生 800 条通话轨迹。同一客户两次通话之间保留本轮形成的客户记忆，属于连续接触，不是两次独立采样。

题目来自公开业务资料与模型辅助标注，客户设定是自建案例，没有真实通话数据。离线质量评分描述这些模拟案例上的表现，不能写成真实客户转化率、品牌内部项目成绩或线上实验结果。

## 先跑一小组

在项目根目录执行。默认只生成计划与预览，**加 `--execute` 才执行**。`--run` 可选：RAG 用它指定本轮目录名；Agent 用它记录运行标签，实际目录始终按模型名和评测日期自动生成。

执行前启动 PostgreSQL + pgvector：`docker compose up -d --wait postgres`，再运行 `uv run growthpilot database init`。连接使用 `.env` 中的 `DATABASE_URL` 与 `DATABASE_SCHEMA`。预览会只读检查知识版本，不创建索引或临时业务 schema；数据库初始化和隔离说明见[数据库文档](../docs/database.md)。

```sh
# 预览骑手场景的前 3 道检索题，不加载检索模型
uv run growthpilot evaluate --suite rag --scenario meituan_rider --limit 3 --run rider-rag-preview
# 使用真实本地检索器执行，无须云端模型密钥
uv run growthpilot evaluate --suite rag --scenario meituan_rider --limit 3 --run rider-rag-run --execute
# 预览 3 个动态客户案例，每位客户计划连续通话 2 次
uv run growthpilot evaluate --suite dialogue --scenario meituan_rider --limit 3
# 小规模观察链路，调用 Agent、独立客户模型会话及独立 judge
uv run growthpilot evaluate --suite dialogue --scenario meituan_rider --limit 3 --repeats 1 --execute
```

`--scenario` 可选 `meituan_rider`、`meituan_merchant`、`didi_driver` 或 `financial_consultation`；省略时运行四场景。`--limit N` 表示**每个场景**最多 N 题。`--case <案例 ID>` 可以重复使用，只选指定案例；ID 从预览产物 `cases.json` 获取。`--repeats` 指同一客户在本轮评测中的连续通话次数，默认 2；同一客户各次通话使用稳定的客户 ID。

对话默认 `--concurrency 16`，表示最多同时评测 16 位不同客户。同一客户从第一次到最后一次通话持续占用一个名额，通话按顺序执行，前一次通话的画像提取收尾完成后才开始下一次，避免后续通话读到未完成的记忆。每次通话的客户对话、画像收尾、judge 评审和资源释放都在并发名额内完成；单条通话内部也保持顺序执行。并发数可改为任意正整数，实际在跑的客户数不超过剩余案例数。它不改变客户数、通话次数或指标分母，也不是模型请求速率限制器。RAG 与离线工程检查不采用此设置，不接受自定义对话并发数。

准备全量对话评测时，先生成无模型请求的计划；报告应显示 400 位客户、每位客户连续通话 2 次、共 800 次计划通话、客户并发上限 16：

```sh
uv run growthpilot evaluate --suite dialogue --concurrency 16
```

正式全量运行时显式加上 `--execute`，结果与预览分别保存：

```sh
uv run growthpilot evaluate --suite rag --run rag-baseline --execute
uv run growthpilot evaluate --suite dialogue --concurrency 16 --execute
```

对话执行需要已配置的 `AGENT_API_KEY` 及运行时知识索引。业务 Agent、模拟客户、通话后画像提取和裁判分别读取 `AGENT_*`、`CUSTOMER_*`、`PROFILE_*`、`JUDGE_*` 环境变量，也可在 `backend/config/models.yaml` 的 `agent`、`customer`、`profile`、`judge` 分组设置模型、温度和输出预算。辅助角色未指定模型、地址或密钥时沿用 Agent 的有效配置，设置对应角色的 `MODEL`、`BASE_URL`、`API_KEY` 即可独立切换 GPT、Qwen 或其他 OpenAI 兼容模型；各角色上下文保持独立。特殊能力通过各自的 `EXTRA_BODY` 显式配置，默认不发送供应商专用参数；不支持温度的模型使用对应角色的 `TEMPERATURE=null`，要求新预算字段的模型设置 `MAX_TOKENS_PARAM=max_completion_tokens`。运行清单记录实际参数，原始用量保留供应商返回的思考 token。无须部署客户专用模型，没有客户角色检查、校准套件、固定客户脚本或消融实验。

## 一、RAG：题目、相关证据、检索结果

阅读顺序为 [题集](datasets/rag/) → [配套语料](datasets/corpus/) → [运行器](rag/runner.py) → [指标](rag/metrics.py)。

每道题保存问题、主题与问题族、`relevant_chunk_ids`，并为每个相关片段保存文档 ID、内容哈希及原文引文。问题族用于识别同一知识点的改写，不能把近义改写当作完全不同的能力。标注按冻结语料判断；相关片段可以有多个。

正式检索题均须在配套知识中有答案，至少标注一个相关片段。无答案、个人审批结果不可知等场景放入端到端对话集，由 Agent 的最终回答接受评价。这样不会给无答案问题硬凑 Recall 分母。

| 指标 | 计算口径 |
| --- | --- |
| Recall@k | 前 k 条中命中的不同相关片段数 ÷ 标注相关片段总数 |
| Precision@k | 前 k 条中命中的不同相关片段数 ÷ k；不足 k 条的空位按不相关处理 |
| MRR@8 | 第一条相关片段在前 8 条中的排名倒数；未命中记 0 |

Recall、Precision 分别报告 `k=1、3、5、8`。同一道题只检索一次，三个指标都使用同一份真实返回排序；重复片段不重复贡献命中。结果按题等权平均，并分别报告四个场景。

执行前校验语料版本、片段归属、文档哈希和引文。当前运行时索引与标注版本一致时直接复用；否则从仓库配套的**完整场景语料**在 PostgreSQL 的独立 RAG namespace 中建立冻结索引，保留非答案片段作为检索干扰项，不改写 `production` 知识库。冻结 namespace 以语料版本生成名称，保留供相同版本后续评测复用；它与每轮对话结束后删除的临时业务 schema 分开管理。本地模型缓存仍可复用，首次准备 BGE 缓存可能下载开源模型，不调用云端生成模型。

语料不匹配时停止发布成绩；单题检索异常会保留错误、原定分母和零分，不能删掉难题提高平均值。更新语料或分块后应重新审核标注、更新版本，不沿用旧成绩。

## 二、文本 Agent：动态客户 → 真实 Agent → 六项指标

阅读顺序为 [客户案例](datasets/dialogue/) → [客户模型](dialogue/customer.py) → [对话运行器](dialogue/runner.py) → [评分 prompt](judges/prompt.md) → [评审与校验](judges/review.py) → [指标](dialogue/metrics.py)。

每个案例分开保存：

- `customer`：画像、初始状态、顾虑、接受条件、拒绝条件和信息披露规则，供客户模型使用。
- `goal`：本案例的合理目标与成功条件，只在对话结束后交给 judge。
- `max_turns`：最多客户轮次；它是运行上限，不是固定客户台词。

Agent 主动开场后，客户模型根据真实回复生成下一句话；后续顾虑和接受决定都在实际对话中发生。客户只看到自己的设定、对话内容和成功短信回执的可见状态，不读取 Agent 内部提示、政策检索结果或评分答案。每条通话建立新的 Agent 会话，同一客户的后续通话通过业务系统原有机制读取本轮已形成的客户记忆；客户模拟器也保留此前对其可见的对话和短信状态，知道之前聊过什么，但不会继承 Agent 内部上下文或隐藏评分目标。客户模拟模型的推理等待不占 Agent 原有最多 300 秒的会话预算，Agent 自身的执行、工具和轮数限制仍然保留。

**每轮完整评测从空客户记忆开始，同一轮内保留真实记忆机制。** 运行器为整轮评测新建独立 PostgreSQL schema；各客户按稳定客户 ID 隔离记忆，同一客户的多次通话共用其画像。本轮不读取生产库或上一轮评测的客户记忆，全部通话及资源关闭后删除临时 schema。运行清单通过 `memory_mode: fresh_database_per_run` 和 `repeat_semantics: sequential_customer_calls` 记录这一方式。无需手动清空生产客户记忆，历史评测报告也不会被当作客户记忆读取。

比较模型或提示版本时，应分别启动新的完整评测，每轮都从空业务 schema 开始，并保持相同题集、通话次数和运行配置。同一轮内的第 1 次和第 2 次通话具有前后依赖，不能把 800 条轨迹当作 800 个独立客户样本，也不能和旧版每次通话单独清空记忆的成绩直接混用。

| 指标 | 回答的问题 | 计算方式 |
| --- | --- | --- |
| `goal_completion`：目标完成度 | 本通电话推进到了什么程度？ | judge 整通打 1～5 分 |
| `problem_resolution`：问题解决度 | 客户的问题、顾虑有没有得到有效处理？ | judge 整通打 1～5 分 |
| `factual_reliability`：事实可靠性 | 业务解释、费用、资格和操作结果是否可信？ | judge 整通打 1～5 分 |
| `communication_quality`：沟通体验 | 是否清楚、自然、简洁，尊重客户意愿？ | judge 整通打 1～5 分 |
| `average_agent_tokens`：每通 Agent token 消耗 | 完成一次对话需要多少主模型资源？ | 代码汇总输入、输出 token，按计划通话计算均值 |
| Agent 首 token 时延（TTFT） | 客户发言后，Agent 需要多久开始输出最终回复？ | 从客户文本提交到最终回复的首个非空文本块，按客户轮次统计 P50、P95，单位秒 |

### 评分标准与裁判输入

完整评分量表与裁判指令集中在 [judges/prompt.md](judges/prompt.md)，运行时直接读取这个 Markdown 文件。四个维度独立评分：1 分表示严重问题，3 分表示已完成部分要求但仍有重要不足，5 分表示该维度要求完整满足；2、4 分分别有明确的中间档位。**没有综合总分，也不再用通过/失败代替质量分。**

裁判只读取三类材料：

1. 本通目标与必要背景，包括目标完成条件、应用名称、客服身份及 Agent 开场实际知道的客户记忆。
2. 客户和 Agent 的实际对话，只保留真正交付给客户的话。
3. 按取得轮次排列的参考原文和工具结果，包括业务资料适用条件、查询结果和短信发送回执。

工具定义及其调用指令、内部控制事件、运行 ID、token 明细、隐藏客户人设和完整业务状态继续保存在 trace 中，不送入裁判。实际取得的业务资料和操作回执仍按轮提供，避免将面向 Agent 的工具调用要求误当评分标准。不能因为材料没有展示挂断等内部控制事件就推断没有执行；告别和是否尊重拒绝仍按实际对话评价。客户已明确结束时，礼貌告别即可，不强求再问是否有其他问题或安排额外下一步；继续纠缠或忽略明确的新问题仍应扣分。

裁判输出使用短 key `goal`、`answer`、`facts`、`tone`，每项只保留 `score` 和一句话 `reason`；空评分额外用 `null_reason` 区分不适用与无法评审。不再要求输出 `evidence`，参考原文和工具回执仍完整保留在输入中。评分 prompt 提供合法 JSON 示例和字段解释；优先按标准 JSON 解析，格式有误时使用 `json_repair` 修复，再提取四个维度及所需字段。额外字段会被忽略并留档；缺少维度、分数越界、非整数评分或空理由仍不通过校验，不补造评分或理由。校验后将四个短 key 映射到报告使用的长指标名称，不改写模型分数和理由。

每通裁判最多请求 3 次，仅对无效输出和临时请求故障重试；合法低分及合法空评分不触发重试。鉴权或配置错误直接报告。`judge/` 保留每次请求的原始输出、解析方式、修复日志、忽略字段、错误与用量，顶层裁判用量累计所有尝试，便于核查容错过程和实际消耗。

目标包括推进、咨询解决与恰当结束拒绝三种。拒绝类案例及时结束可以得到目标 5 分；推进类案例中客户暂缓，则可以目标完成度一般、沟通体验较好。后续通话结合开场记忆与本通进展评分，已经完成的前置步骤无需重做，也不因未再次同意接收下载入口而扣分；本通需要处理的疑问和下一步仍须完成，不能仅凭历史进展自动给满分。客户自述完成不等于平台核验，新的短信操作仍需本通授权，短信发送成功不等于客户完成注册。

评分范围限定为本通目标、客户实际问题及必要前提；客户计划自行核实或已明确暂缓的事项，不自动成为 Agent 必须补充的清单。资料同时包含一般规则与专项要求时，应核对当前业务对象和适用条件，不能仅凭一般可选项认定专项要求可以替代。

本项目骑手场景评测将“美团骑手 App”与“美团众包 App”按同义称呼处理，任何维度都不因名称差异扣分；众包与专送的实际政策、资格和流程仍分别核对。此规则是本项目的评分约定，不表示现实中两个应用或配送模式相同。

事实可靠性区分**依据不足、事实错误与遗漏回答**。可信业务配置、当时已取得的参考资料和明确归因的客户自述都可提供相应支持；不能因为没有检索就自动判成事实错误。客户自述不升级为官方核验，后续取得的资料不能为先前回答补证。漏答申请费主要影响问题解决度；把未知费用说成确定金额则影响事实可靠性。明确表达为粗估或建议的合理近似、区间和预算余量可以得满分，不要求每个数字对应检索原文或提供精确公式；明显不合理的外推、与已知事实冲突或冒充确定报价仍应扣分。先判断维度是否适用：没有可评业务事实时，事实维度必须记“不适用”，不能因为没有说错话而给满分；没有实质业务问题的简单拒绝，其问题解决度也记“不适用”，尊重拒绝由目标完成度和沟通体验评价。记录缺损等无法评审的情况记“未知”，不用 3 分补齐。

### 汇总与工程指标

每个质量维度展示均分、1～5 分分布、已评分/不适用/未知数量及覆盖情况，并列出 1～2 分的案例、理由和 trace 链接。总览、四个场景和案例目标类型使用相同口径；不把四项分数加权成总分，也不将模拟客户分数写成真实业务转化率。

每通 Agent token 包含主对话内工具循环产生的全部模型用量，不混入客户模型、judge 或通话结束后的画像提取；这些辅助用量单独保留。

**响应时延采用首 token 时延（TTFT）。** 从本轮客户文本提交给 Agent 开始计时，到最终面向客户的回复首个非空文本块到达为止，以流式文本块近似首 token。它包含此前的推理、工具执行和多次模型调用等待；内部思考、工具参数、工具结果，以及最终被丢弃的中间说明都不作为首 token。结束工具直接提供告别文本时，按告别文本可用时间计。主动开场、模拟客户生成、judge 评审和通话后画像提取不纳入客户轮时延。

该指标测量 Agent 端开始提供回复文本的时间，不等于浏览器显示首字或客户听见首音的延迟，不含 ASR／TTS。每轮 trace 的 `first_token_seconds` 保存 TTFT，`elapsed_seconds` 继续保存完整回复耗时，仅供诊断。P50 表示一半已观测轮次的首 token 时延不超过该值，P95 用于观察较慢响应；分位数使用排序位置 `(n−1)×p` 线性插值。失败或空回复另行计数，不当作零时延。

时延口径版本为 `agent-first-token-v1`，保存在运行清单及汇总的 `latency_version`；主指标字段为 `agent_first_token_latency_p50_seconds` 和 `agent_first_token_latency_p95_seconds`。旧 trace 未采集 `first_token_seconds` 时按缺测处理，不从完整回复耗时推算。旧版 `agent_response_latency_*` 与首 token 指标不可直接比较；原来的完整回复耗时不能改标为 TTFT，需要重新执行才有新口径成绩。

模型调用失败、judge 无效、未运行和 usage 缺失分别留档，不当成低分或零消耗。未知项存在时，不发布该项完整均分；已取得评分的观察均分可供诊断，但同时显示覆盖率，不冒充全量成绩。一项缺测不会抹掉其他完整取得的指标，整轮仍标为未完成。同一客户的连续通话全部纳入，不挑成绩较好的一次。时延统计同时展示已测轮次、缺失轮次与未完整记录的通话，避免只报告快且成功的部分。

评分版本为 `dialogue-rubric-v3.2.3`；运行清单保存版本、实际评分 prompt 的源码路径、快照路径和 SHA256。每个新对话运行（包括预览）在 `judge_prompt.md` 冻结实际加载的提示词，报告链接这份快照，便于之后修改源码仍可复查原评分口径。v3.2.3 明确按已有进展、剩余要求和本通新增问题评价连续通话，不要求重复客户明确表示已完成的查询或说明；保留骑手应用名称的同义评审约定，保留短 key、分数与理由及合理估算口径，不向裁判提供工具定义；扣分前逐轮核对已有回答，只按影响当前问题或目标的实际缺口判断，并保留自然收尾及条款适用范围规则。思考模式与推理强度按本次 `JUDGE_*` 配置及运行清单核对。重评必须另存、保留原始结果并说明复用了原对话，分数变化不代表 Agent 能力变化。**旧版“目标达成率、事实有据率、平均 token”三指标报告不能与分档评分直接比较。** 比较不同 Agent 模型时，应使用同一评分版本、量表、裁判模型、题集和运行配置。

### 画像处理与连续通话

每通结束后，系统会把本通客户提供的新信息提取到画像，供下一通读取。例如客户已说明所在城市、已经下载应用，下一通可据此继续沟通。如果提取失败或超时，下一通可能缺少这些信息。

报告的 `profile_processing` 按整体、场景和目标类型单列画像处理状态，区分成功、跳过、失败、超时、未采集等情况，并列出可能受影响的后续通话。历史记录缺少字段表示未知，不等于提取失败。这是记忆处理完整性提示，不自动改写裁判分数；即使质量评分完整，也应检查画像状态后再解释连续通话效果。

### 只补跑失败裁判

对话已成功完成、但裁判未取得有效结果时，可以复用原始对话，只重新请求失败的裁判。先预览，再显式执行；把示例中的目录名替换为实际来源运行：

```bash
uv run growthpilot evaluate --suite dialogue --retry-judge-from agent/deepseek-flash_2026-11-02_20-25-06
uv run growthpilot evaluate --suite dialogue --retry-judge-from agent/deepseek-flash_2026-11-02_20-25-06 --execute
```

`--retry-judge-from` 接受 `agent/<目录名>`，也接受能够唯一定位的目录名，并兼容旧版平铺目录。补跑结果使用来源中的 Agent 模型名和本次日期新建目录；预览仍写入 `.run/evaluation-previews/agent/`。

补跑保留合法低分及合法空评分，只处理缺失或无效评分，不重新执行客户、Agent、工具和画像提取。它读取原运行的案例、轨迹和配置快照，保留原始证据并另存结果；Agent 用量、TTFT 和记忆状态仍来自原对话，不能当作新一轮端到端成绩。原运行的资源一致性异常也不会被补裁判消除。

为避免同一份成绩混用口径，局部补跑要求裁判版本、提示词、模型及生成配置一致。更换评分口径后应启动新评测。Agent 或客户本身执行失败时，使用 `--case` 选择该客户，重新执行完整的连续通话序列；不能只重跑第二通并假设已经恢复第一通记忆。

补跑会逐字冻结原始产物并校验哈希。如果旧产物包含本机绝对路径，会在创建新报告前拒绝复制，避免泄漏继续传播，也避免脱敏后沿用原始证据的旧哈希。请使用当前版本重新生成这类旧记录。

## 三、看报告和追溯一次失败

正式结果按两类保存：

- RAG：`evaluation/reports/rag/<run>/`。使用 `--run` 指定目录名；省略时按检索模型名和日期自动命名。
- Agent：`evaluation/reports/agent/<模型名_YYYY-MM-DD_HH-MM-SS>/`，例如 `deepseek-flash_2026-11-02_20-25-06`。时间使用北京时间，包含时分秒以区分同一天的多轮评测；同秒重名时自动加序号。模型名中的 `/` 等路径字符会替换为 `-`。可选的 `--run` 只写入 `manifest.json` 的 `run_label`，不改变目录名。

每轮目录直接包含下表所列文件，作为教学成果随源码提交到 Git。保留运行清单、案例快照、原始结果、裁判记录和汇总，让学员能够从成绩追溯到具体证据；失败和缺测也一并展示，不能只提交成绩摘要。预览保存在 `.run/evaluation-previews/rag/` 或 `.run/evaluation-previews/agent/`，工程检查保存在 `.run/checks/`，不混入正式报告目录。

2026-11-02 的正式 RAG、Agent 全量运行及独立补跑已按此结构归档，见[本轮评测记录](reports/README.md)。迁移只调整文件位置，原全量 Agent 运行的未完成状态和补跑结果分别保留，没有合并成一份完整成绩。

| 文件 | 阅读用途 |
| --- | --- |
| `manifest.json`、`cases.json` | 本次客户选择、连续通话次数、客户并发上限、记忆隔离方式及代码/提示/模型/语料版本 |
| `judge_prompt.md` | 本次对话裁判实际使用的完整评分 prompt 快照，预览也保存 |
| `report.md`、`summary.json` | 同一份统计结果的人读版和结构化版 |
| `rag_results.json`、`rag_summary.json` | RAG 每题原文检索结果、相关片段和指标 |
| `traces.json` 或 `traces.json.gz` | 对话原文、工具与 Skill 事件、检索证据、用量和结束原因；聚合原文达到 50 MiB 时自动无损压缩 |
| `traces/` | 每条案例的实时保存文件；结束或中断时汇总为 `traces.json`（大文件为 `traces.json.gz`），避免全量运行反复重写历史轨迹 |
| `judge/` | 每条对话的裁判原始输出、用量和校验错误 |

压缩仅改变聚合轨迹的保存格式，不改变对话、评分或记录顺序；回放和裁判补跑均能直接读取两种格式，报告链接也会指向实际文件。逐通 `traces/` 与 `judge/` 文件保持可直接阅读的 JSON。

查看某轮结果时可以直接打开 `report.md`；回放 Agent 对话使用 `uv run growthpilot replay --run agent/deepseek-flash_2026-11-02_20-25-06`，也支持能够唯一定位的目录名和旧版平铺目录。RAG 的逐题检索结果保存在对应目录的 `rag_results.json` 中。

对话运行清单只读记录实际知识索引的语料版本、模型签名和分块数量；执行结束再次核对知识与代码资源。若运行期间版本变化，状态标为 `invalidated`，保留轨迹但不发布正式指标。预览不会创建索引或加载向量模型。

先看报告状态与缺测数，再看指标；从低分案例进入原始 trace，判断是资料缺失、检索没找到、Agent 回答用错，还是评审未完成。judge 输出须符合四维量表和 JSON 结构；格式错误或临时请求故障最多独立重评 3 次，合法低分和合法空评分不重试，也不为挑选高分重跑。格式有效不代表评分正确，应结合理由和原始材料复核。

## 目录与工程检查

```text
evaluation/
├── datasets/       # 按四场景组织的 RAG、客户案例与完整语料
├── rag/            # 检索执行与三个检索指标
├── dialogue/       # 唯一的动态客户对话运行方式
├── judges/         # 简洁评分 prompt、输入整理与四维评审
├── common/         # 题集选择、trace、保存与报告
├── checks/data/    # 历史知识探针输入，不计入正式题集
└── reports/        # 正式评测记录与总览
    ├── rag/        # 每轮 RAG 检索结果
    │   └── <run>/
    └── agent/      # 每轮 Agent 端到端结果
        └── <模型名_YYYY-MM-DD_HH-MM-SS>/
```

`tests/evaluation/` 测试评测程序本身的分母、异常、证据与协议；`tests/agent_harness/` 继续保护 Memory 持久化、Skill 加载权限及业务计算等运行时功能。它们不评价某个 Memory/Skill 开关的收益。

工程契约、知识覆盖和语音探针的代码与输入统一放在 `evaluation/checks/`，新检查产物写入 `.run/checks/`，仅用于工程检查与问题定位，现有 `growthpilot` 工程命令保留。本轮已经取得的工程检查证据保存在对应 Agent 运行的 `checks/` 下，与该轮评测一起追溯。知识探针的固定追问不是第二套正式对话评测。不同口径的报告不能直接比较。具体兼容命令见 [工程检查说明](checks/README.md)。
